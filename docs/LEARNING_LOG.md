  - `aiogram==3.12.0`

  - `aiohttp==3.10.0`

### ⚠️ Проблемы и решения
| Проблема | Решение | Вывод |
|----------|---------|-------|
| `python --version` показывал 3.13.4 вместо 3.14.0 | Использовал `py -3.14 -m venv .venv` для явного указания версии | Несколько версий Python могут сосуществовать; важно явно указывать нужную |
| Ошибка компиляции `pydantic-core` при установке зависимостей | Отложил установку `pydantic` до этапа конфигурации; начал с минимального набора | Не все библиотеки сразу имеют wheels для новой версии Python — стартуйте с минимума |
| Команда `rmdir /s /q` не работала в PowerShell | Использовал `rmdir -Recurse -Force .venv` (синтаксис PowerShell) | CMD и PowerShell имеют разный синтаксис — важно знать среду |

### 💡 Ключевые открытия
- Виртуальное окружение изолирует зависимости — критически важно при работе с разными проектами
- `.gitignore` — первый барьер против утечки токенов. Проверяю ДО каждого коммита: `git status`
- Python 3.14.0 требует обновлённого `pip` для корректной установки зависимостей: `python -m pip install --upgrade pip`

## 2026-02-16 — День 3: Архитектура и расширение функционала

### ✅ Сделано
- Вынесены обработчики в отдельный модуль `src/bot/handlers.py`

- Обновлена архитектура: чистая точка входа в `main.py`, вся логика в `handlers.py`

### ⚠️ Проблемы и решения
| Проблема | Решение | Вывод |
|----------|---------|-------|
| Сложность тестирования асинхронных обработчиков | Изучил `pytest-asyncio` и `AsyncMock` | Асинхронный код тестируется так же, как синхронный — с правильными инструментами |
| Дублирование логики в `main.py` | Вынес все обработчики в отдельный модуль | Чистая архитектура = меньше багов при расширении |

### 💡 Ключевые открытия
- Роутеры aiogram 3.x позволяют легко масштабировать бота — просто добавляй новые файлы с обработчиками
- Тестирование через моки (`MagicMock`, `AsyncMock`) изолирует логику от внешних зависимостей
- Заглушки (`/flight`) важны для пользовательского опыта — пользователь видит, что функционал «в разработке», а не «сломан»
## 2026-02-21 — День 5: Интеграция с OpenSky через OAuth2 (Этап 3 завершён)

### ✅ Сделано
- Изучена актуальная документация OpenSky API
- Выявлено критическое изменение: базовая аутентификация (логин/пароль) НЕ РАБОТАЕТ для аккаунтов после марта 2025
- Реализована поддержка OAuth2 Client Credentials Flow:
  • Создан API client в аккаунте OpenSky
  • Получены client_id и client_secret
  • Реализован клиент с автоматическим получением access token
  • Добавлена обработка истечения токена (30 минут) и автоматическое обновление
- Успешная интеграция: бот получает реальные данные о рейсах из эфира
- Добавлена резервная заглушка при недоступности API

### ⚠️ Проблемы и решения
| Проблема | Решение | Вывод |
|----------|---------|-------|
| Постоянная ошибка 401 при корректных данных | Изучил документацию → обнаружил переход на OAuth2 для новых аккаунтов | Всегда проверяйте актуальную документацию перед интеграцией — политики аутентификации меняются |
| Сложность отладки аутентификации | Написал изолированный тестовый скрипт `test_oauth2.py` | Изолированные тесты экономят часы отладки |
| Токен живёт 30 минут | Реализовал кэширование с автоматическим обновлением за 5 минут до истечения | Для продакшена критично обрабатывать временные ограничения токенов |

### 💡 Ключевые открытия
- Современные API всё чаще требуют OAuth2 вместо базовой аутентификации
- Токены с ограниченным сроком действия — стандартная практика безопасности
- Для РФ критично выбирать сервисы с поддержкой современных методов аутентификации (без привязки к географии)
